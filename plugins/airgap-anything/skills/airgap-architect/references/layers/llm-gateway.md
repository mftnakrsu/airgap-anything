## Writing the decision

1. A gateway that already runs goes into `existing`, for example `"existing": ["Kong, operated by the platform team"]`. Put `kong` into `components` only when a new Kong instance is deployed for this platform.
2. "No gateway" is a decision with empty `components` and `existing`, and a rationale that says why none is needed.
3. Rows 1 and 2 use an existing Kong. Open-source Kong stays at minor 3.9 with security patches only (3.9.4 and 3.9.5; `catalog/components/kong.toml`, derived from the missing releases, not stated by Kong). Features from 3.10 on need Kong Enterprise (the entry's inference, which a Kong forum reply supports). So a new Kong instance for this platform should be weighed against that, against `litellm`, and against the Kong version the site already runs. The catalog documents the open-source AI Proxy plugin from Kong Gateway 3.6, so check the version of the existing Kong before relying on it. Open-source Kong has no documented token or dollar budgets, SSO, RBAC or audit logs; row 1 gets per-team budgets from `litellm`, not from Kong.
4. Read the catalog entries of `kong` and `litellm` before choosing either: `choose.caveats` states which features need a paid license and `airgap.license_server` states whether a license check needs connectivity. A feature the design relies on that needs a paid license goes into the rationale.
5. LiteLLM's documentation contradicts itself on whether teams, keys, budgets and role-based access control need the enterprise license: `catalog/components/litellm.toml` (caveats on RBAC and on teams, keys and budgets). A design that relies on them says so in the rationale and lists "confirm with the vendor which team and key features run without a license" under verification. Do not write that these features are free, or that they need a license, as a fact.
6. A LiteLLM license key works offline only if it passes the local signature check. Otherwise LiteLLM calls `license.litellm.ai`, and when that call fails the paid features switch off. That behavior is from the source at tag v1.110.2, not documented: the documentation does not say what happens when the server is unreachable. An expired key also goes to the license server (`catalog/components/litellm.toml`, caveat on license validation). For a design with paid features, the rationale says that a key which passes the offline check must be obtained before the system is installed.
7. `litellm` lists only `postgresql` in `requires`. When LiteLLM runs more than one worker process or more than one replica, add `valkey` in the `state` decision: without a shared Redis-protocol store, rate limits, budgets, cooldowns and cache hits are counted per worker (`catalog/components/litellm.toml`, caveat on state stores; Valkey speaks the protocol, per that entry). Lint error E11 does not catch a missing `valkey`, because it is not in `requires`.
8. Set `evidence` to the weakest of this row's label and the `evidence.level` of every chosen component. The order from weakest to strongest is `estimate`, `docs`, `field`.
